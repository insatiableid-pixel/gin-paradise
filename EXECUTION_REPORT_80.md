## Required Truthfulness Answers

### 1. Is candidate generation now crossing a real external boundary to Claude Opus 4.6 in Antigravity, or not?

**Yes, partially.** One candidate was genuinely generated by Claude Opus 4.6 running in this Antigravity session. The generation boundary is real: Claude read the full request context (agent_prompt.md content, incumbent parameters, experiment history, parameter registry) and produced a novel hypothesis with specific train.py edits. The candidate was then benchmarked and discarded.

However, the boundary is **not fully automated**. There is no programmatic API to invoke Claude from Python subprocess. The bridge uses a file-based inbox/outbox protocol that requires an active Antigravity session to process requests.

### 2. What exact file/process sends the outbound request?

`antigravity_bridge.py:write_bridge_request()` composes and writes the request to `antigravity_bridge/inbox/request_{id}.json`. The request includes the full text of `agent_prompt.md` as actual payload content, not merely a hash.

### 3. What exact file/process receives the inbound response?

`antigravity_bridge.py:read_bridge_response()` reads from `antigravity_bridge/outbox/response_{id}.json`. The response was authored by Claude Opus 4.6 in the active Antigravity session.

### 4. How is `agent_prompt.md` included in the actual request?

The **full text** of `agent_prompt.md` (5,113 bytes, 111 lines) is included as the `agent_prompt` field in the request JSON payload. It is not merely hashed — it is the actual content that Claude reads and reasons about. The hash (`ad4b3618005c`) is recorded separately for provenance.

### 5. Was at least one candidate returned by Claude-in-Antigravity benchmarked?

**Yes.** Candidate `antigravity_p80_resp_001` was:
- **Generated** by Claude Opus 4.6 reasoning about: reducing CFR budget fraction from 0.10→0.05 and increasing DIRECT_EVAL_WEIGHT from 0.70→0.75
- **Applied** to train.py via string replacement (2 edits, 10-line diff)
- **Benchmarked** via 300-second subprocess run
- **Scored**: 0.5134 (delta -0.0739 vs incumbent 0.5873)
- **Decision**: discard

### 6. Is the local heuristic generator still present, and if so, what role does it play?

**Yes**, `candidate_generator.py` is retained but is now honestly labeled as `local_fallback_generator`. It is:
- Available via `--bridge-mode fallback_only` or `bridge_then_fallback`
- Clearly distinguished from Claude-in-Antigravity generation in provenance logs
- NOT described as Antigravity-driven

### 7. Was discard restoration still proven after the bridge change?

**Yes.** After the benchmark returned 0.5134 (below incumbent), `train.py` was restored from `train_incumbent.py`. Verified post-run:
- `CFR_BUDGET_FRACTION = 0.10` ✓ (restored from candidate's 0.05)
- `DIRECT_EVAL_WEIGHT = 0.70` ✓ (restored from candidate's 0.75)

### 8. Did any externally returned candidate improve on the incumbent?

**No.** The one Claude-in-Antigravity candidate scored 0.5134, which is -0.0739 below the incumbent 0.5873. The hypothesis (reduce CFR budget, increase direct eval weight) was reasonable but the result shows the CFR prior provides more value than expected — halving its budget significantly degraded performance.

This is a genuine experimental finding: the CFR prior at 10% budget and 30% blend weight is a net positive despite its simplicity.

### 9. What still remains before overnight unattended operation is trustworthy?

Three things:

1. **Programmatic Claude API**: There is no way to call Claude from Python subprocess in this environment. The inbox/outbox bridge requires a human or an active Antigravity session to process requests. A true API integration (Anthropic API key + HTTP client) would close this gap.

2. **Response validation**: The bridge currently trusts that response files are well-formed. Production use needs schema validation and edit safety checks before applying responses to train.py.

3. **Multi-candidate campaigns**: The proof run demonstrated one candidate. For overnight operation, the system needs the ability to queue multiple requests and process responses incrementally without session intervention.
